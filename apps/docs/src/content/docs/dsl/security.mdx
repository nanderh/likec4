Elements and relationships can carry known **vulnerabilities** (CVEs, pentest findings) and
**threats** from [STRIDE](https://learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-threats) threat modelling.
They are displayed in the element details (_Vulnerabilities_ and _Threats_ tabs),
in the relationship popover, as a badge on diagram nodes with unresolved items,
and can color the diagram by risk.

## Vulnerabilities

```likec4
model {
  gateway = system 'Gateway' {
    vulnerability CVE-2024-3094 'xz/liblzma backdoor' {
      severity critical
      cvss 10.0
      vector 'CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:C/C:H/I:H/A:H'
      cwe CWE-506
      status open
      description 'Malicious code in upstream tarballs'
      mitigation 'Pin xz to 5.4.6'
      link https://www.openwall.com/lists/oss-security/2024/03/29/4
    }
  }
}
```

| Property      | Values                                                                                 |
| ------------- | -------------------------------------------------------------------------------------- |
| `severity`    | `critical`, `high`, `medium`, `low`, `info` (derived from `cvss` if omitted)            |
| `cvss`        | CVSS base score, `0.0` - `10.0`                                                         |
| `vector`      | CVSS vector string                                                                      |
| `cwe`         | Weakness id, e.g. `CWE-79`                                                              |
| `status`      | `open`, `in-progress`, `mitigated`, `accepted`, `transferred`, `resolved`, `false-positive` |
| `title`, `description`, `mitigation` | text or markdown                                                 |
| `link`        | one or more links                                                                       |

Identifiers like `CVE-...`, `GHSA-...` and `CWE-...` link to NVD, GitHub advisories and MITRE automatically,
unless the vulnerability has its own links.

## Threats

```likec4
model {
  gateway = system 'Gateway' {
    keyStore = store 'Key Store' {
      threat KS-T1 'Extraction of device private keys' {
        stride information-disclosure, spoofing
        likelihood low
        impact critical
        status mitigated
        mitigation '''
          Keys never leave the **TEE**
        '''
      }
    }
  }
}
```

| Property                | Values                                                                  |
| ----------------------- | ----------------------------------------------------------------------- |
| `stride`                | one or more of `spoofing`, `tampering`, `repudiation`, `information-disclosure`, `denial-of-service`, `elevation-of-privilege`, or the letters `S`, `T`, `R`, `I`, `D`, `E` |
| `likelihood`, `impact`  | `low`, `medium`, `high`, `critical`                                     |
| `risk`                  | `low`, `medium`, `high`, `critical` (derived from likelihood × impact if omitted) |
| `status`                | same as for vulnerabilities                                             |
| `title`, `description`, `mitigation` | text or markdown                                           |
| `link`                  | one or more links                                                       |

Threats and vulnerabilities without `status` are considered `open`.

Statuses fall into three groups:

| Group        | Statuses                                  | Meaning                                       |
| ------------ | ----------------------------------------- | --------------------------------------------- |
| unresolved   | `open`, `in-progress` (or no status)      | still to be addressed                         |
| risk carried | `accepted`, `transferred`                 | the risk remains, someone owns it             |
| closed       | `mitigated`, `resolved`, `false-positive` | the risk is gone                              |

Nodes show a badge with the number of unresolved items, colored by the highest severity or risk,
and a muted second marker when the element has items with carried risk.

### Parent elements

Badges and _Color by_ of an element include everything inside it: its own items, the items of its
descendants, and of relationships between its descendants. A collapsed parent, like `gateway`
in a landscape view, shows the risk of its children. The tooltip of the badge separates own items
from items inherited from children.

A scoped view (`view gatewayDetail of gateway`) does not always show the scope element itself,
for example when its children are placed in groups. Then a badge next to the view title shows the
unresolved items of the scope element and of its relationships; click it to open the element details.

### Data flows

STRIDE-per-interaction threats are defined on relationships:

```likec4
model {
  gateway -> pki 'CMP' {
    threat DF-T2 'Denial of service on CMP endpoint' {
      stride D
      risk medium
    }
  }
}
```

The _Threats_ tab of an element lists its own threats, the threats of its direct relationships,
and, in a separate section, the threats inherited from its children, with a STRIDE summary on top.

## Threat register

When the model has vulnerabilities or threats, the navigation panel shows a **Threat register** button.
It opens a window with all threats and vulnerabilities of the project, of elements and of relationships:
type, id, title, element or relationship, STRIDE, likelihood, impact, risk (severity for vulnerabilities) and status.

- Click a column title to sort, the filter icon next to it to filter.
- Click a row to show the element or relationship in a view: the current view if it contains it,
  otherwise the first view that does.
- The details button at the end of a row opens the element details (or relationship details).
- **Export CSV** downloads the filtered and sorted rows.

The window stays open while you navigate, and can be moved and resized.

## Color by risk

When the model has vulnerabilities or threats, the navigation panel shows a **Color by** menu (palette icon).
It recolors all nodes of every view, similar to label sets in other tools:

| Mode                   | Node color                                                    |
| ---------------------- | ------------------------------------------------------------- |
| Element colors         | own colors (default)                                          |
| Highest risk (all)     | highest of vulnerability severity and threat risk             |
| Vulnerability severity | highest severity of unresolved vulnerabilities                |
| Threat risk            | highest risk of unresolved threats                            |
| Risk score             | highest likelihood × impact of unresolved threats (1 - 16)    |

The color is the highest severity or risk of the unresolved items (`open`, `in-progress` or without status).
Elements without unresolved items are purple when some risk is carried (`accepted`, `transferred`),
blue when all items are closed (`mitigated`, `resolved`, `false-positive`), and muted without items.
_Risk score_ gives more variation when most threats have the same risk level: it colors by the cell of the
4 × 4 risk matrix (likelihood × impact, 1 to 16), and the legend shows the matrix. Threats without
both likelihood and impact use their risk level (low 1, medium 4, high 9, critical 16).
Vulnerabilities are not part of this mode.

The selected mode is kept while navigating between views (per browser session).

This is a viewer setting and does not change the views. To keep a colored version of a view,
for example in an exported site, use a [style group](/dsl/views/predicates/) with tag-based rules
in a view that `extends` the original.

## Separate threat model

Use [`extend`](/dsl/extend/) to keep the threat model in separate files, next to the architecture:

```likec4
// threats.c4
model {
  extend gateway.keyStore {
    threat KS-T2 'Unauthorised PKCS#11 operations' {
      stride elevation-of-privilege
      likelihood medium
      impact high
    }
  }

  extend gateway -> pki 'CMP' {
    threat DF-T3 'Replay of CMP messages' {
      stride tampering, repudiation
    }
  }
}
```

<Aside type='note'>
Identifiers should be unique in the project. Validation warns when the same threat or vulnerability
identifier is defined on more than one element or relationship. If an `extend` defines an identifier
again for the same element or relationship, the first definition wins, also with a warning.
</Aside>

An `extend` of a relationship must match the relationship by source, target, kind, title and direction.
When it matches nothing, the warning lists the nearest relationships: those between the same elements,
otherwise those from the same source or to the same target, by similarity of the title.
